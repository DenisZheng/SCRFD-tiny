# 与 ESP-DL MSR+MNP 的尺度对齐对比分析

**日期：** 2026-10-16
**目的：** 判断 SCRFD-tiny @320 是否值得迁移到 ESP-DL，替代官方 MSR+MNP。
**结论：** 值得。在目标部署尺度下我们的模型精度明显更高。

---

## 1. 为什么要做这个分析

计划把 SCRFD-tiny 转成 `.espdl` 用于 ESP32-S3/P4。在投入量化与上板工作前，
需要回答一个问题：**转换后能否达到（或接近）ESP-DL 官方 MSR+MNP 的水平？**

直接对比两边的公开数字会产生严重误导：

| 模型 | 公开 mAP50-95 | 验证集 |
| --- | --- | --- |
| ESP-DL MSR+MNP (s8_v1) | 0.367 | **未公开的 custom val set** |
| SCRFD-tiny @320（本仓库） | 0.167 | **WIDER Face 官方 val 全集** |

两者相差 2.2 倍。但**这不是模型能力差异，而是验证集难度差异**。本文件用数据证明这一点，
并给出尺度对齐后的可比数字。

---

## 2. 根因：WIDER val 对嵌入式模型来说「太小了」

### 2.1 事实

- WIDER val **全部 3226 张图的宽度都是 1024 px**
- 我们的模型输入 **320×320**，缩放比 = 1024/320 = **3.2**
- MSR 输入 **120×160（高×宽）**，缩放比 = 1024/160 = **6.4**

### 2.2 WIDER val 的人脸在各自输入空间的尺寸

| 原图脸宽 | 占比 | 缩放到我们的 320 输入 | 缩放到 MSR 的 160 输入 |
| --- | --- | --- | --- |
| 0–8 px | 17.3% | **0.0–2.5 px** | 0.0–1.2 px |
| 8–16 px | 32.4% | 2.5–5.0 px | 1.2–2.5 px |
| 16–32 px | 25.8% | 5.0–10.0 px | 2.5–5.0 px |
| 32–64 px | 15.4% | 10.0–20.0 px | 5.0–10.0 px |
| 64–128 px | 6.1% | 20.0–40.0 px | 10.0–20.0 px |
| 128+ px | 3.0% | 40.0+ px | 20.0+ px |

上表由 `data_align.py` 实测生成（读取 39697 个 GT 框与 3226 张图的实际尺寸）。

### 2.3 直接后果

| 判据（按其自身输入空间的 stride-8） | 我们的模型 @320 | MSR+MNP |
| --- | --- | --- |
| 输入空间不足 8 px（小于 1 个格子） | **68.9%** 的脸 | **87.5%** 的脸 |
| 输入空间 ≥32 px（4+ 个格子，可靠） | 4.3% 的脸 | 1.3% 的脸 |

**MSR+MNP 的 anchor 是 16/32（stride 8）和 64/128（stride 16），其输入空间里
小于 16 px 的脸基本检测不到**——对应原图小于 102.4 px 的脸，而 WIDER val 中
这类脸占 **91%**。

因此 **MSR+MNP 不可能在 WIDER val 上得到 0.367**。它那个数字必然来自一个人脸
尺寸正常的业务验证集。同理，我们的 0.167 也不能说明模型差。

---

## 3. 尺度对齐后的对比方法（方案 C）

### 3.1 子集定义

只保留「**图内所有人脸都可被 MSR+MNP 检测**」的图片：

```
筛选条件：图中每个人脸宽 >= 102.4 px
推导：MSR 输入 160 宽，最小 anchor 16 px，WIDER val 图宽 1024 px
      102.4 = 16 × (1024 / 160) = 16 × 6.4
```

结果：**957 图 / 1253 脸**（占原 val 的 29.7% 图、3.2% 脸）。

### 3.2 评估方式

用自实现的 COCO 式评估（IoU 0.50~0.95，10 个阈值取平均），
GT 来自转换后的 val 标注，预测来自两个 checkpoint 的相同导出流程。

### 3.3 结果

| 模型 | mAP50-95 | AP50 |
| --- | --- | --- |
| **微调 `ft320-20261015` @尺度对齐子集** | **0.6656** | **0.9603** |
| 基线 `weights/best.pt` @同子集 | 0.6527 | 0.9543 |
| **ESP-DL MSR+MNP（custom val set，未公开）** | **0.367** | 未公开 |

### 3.4 同一模型在两种验证集上的差距（关键证据）

| 验证集 | mAP50-95 | AP50 |
| --- | --- | --- |
| 尺度对齐子集（1253 脸） | **0.6656** | 0.9603 |
| WIDER val 全量（39697 脸） | **0.1647** | 0.3296 |

**同一个 checkpoint，因验证集不同，mAP50-95 相差 4.0 倍（0.165 → 0.666）。**

这直接证明：**0.167 这个数字低是验证集难度造成的，不是模型能力问题。**

---

## 4. 结论与决策依据

### 4.1 结论

**在目标部署尺度下，SCRFD-tiny @320 的精度（0.666）约是 MSR+MNP 报告值（0.367）的 1.8 倍。**

### 4.2 其他有利因素

| 维度 | SCRFD-tiny @320 | MSR+MNP |
| --- | --- | --- |
| 结构 | 单阶段，一次前向 | 两阶段，MNP 按候选数逐个精修 |
| 延迟特性 | **不随人脸数增长** | 每多一个候选多一次 48×48 推理 |
| 输出 | 框 + 5 点关键点 | 框 + 5 点关键点（功能对等） |
| 模型体积 | 432 KB (fp32)，量化后预估 ~110 KB | 186.6 KB (int8) |
| 计算量 | 112.8 MMACs @320 | MSR 120×160 + N×MNP 48×48 |

**延迟优势在多人脸场景会非常明显**：MSR+MNP 的 MNP 延迟 = 5.3 ms × 候选数（S3），
一张 20 人脸的图仅 MNP 就要 106 ms。

### 4.3 决策

**值得继续做 `.espdl` 转换与上板测试。**

---

## 5. 必须保留的不确定性（不可省略）

1. **子集样本量小**：1253 脸 vs 全量 39697 脸，统计置信度有限，但趋势明确。
2. **ESP-DL 的 custom val set 内容未知**：它可能比我们的筛选子集更难或更容易。
   **0.666 vs 0.367 是「尺度对齐后的粗略比较」，不是严格同集对比。**
3. **精度口径不同**：我们是 fp32 PyTorch 推理，MSR+MNP 是 int8 量化模型。
   量化通常带来 1~3 个点损失，实际部署后我们的数字会略降（即使降 3 点仍在 0.63 左右）。
4. **本分析只评检测框，不评关键点**：WIDER val 无关键点标注，两边都无法给出
   关键点精度对比。MSR+MNP 的关键点质量只能在上板后用实际图片抽检。
5. **未实测**：`.espdl` 无法在 PC 上运行，本文件全部为数据侧推算 + PyTorch 侧实测，
   **最终裁决仍需上板同图对比。**

## 6. 复现方式

本目录已内置两个脚本，直接运行即可：

```bash
# 1) 数据分布与能力边界分析
python3 docs/evaluation/data_align.py \
    <val_labels_dir> <val_images_dir>

# 2) 尺度对齐子集上的对比评估
python3 docs/evaluation/plan_c_compare.py \
    <val_labels_dir> <preds_finetuned_dir> <preds_baseline_dir> [out_json]
```

实测调用例（服务器上的相对路径）：

```bash
cd /root/scrfd-tiny-lab/runs
python3 data_align.py
python3 plan_c_compare.py /root/scrfd-tiny-lab/datasets/WIDERFace/labels/val \
    ft320-20261015/wouts baseline320/wouts cmp-subset/compare-report.json
```

依赖：`numpy`、`opencv-python`（仅 data_align 读图尺寸用）；
不需要 pycocotools，mAP 为脚本内自实现。

预测目录由 [tools/export_wider_preds.py](../../tools/export_wider_preds.py) 生成。

两个脚本均已在服务器实际运行并复现本文数字（2026-10-16）。
